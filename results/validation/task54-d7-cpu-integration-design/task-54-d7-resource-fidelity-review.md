## 1. Evidence and concrete findings

### F1 — The alternative must preserve the operating rule actually in force

`docs/post-full-queue.md:21,59–69` requires sequential controlled work, nice10, per-job12/aggregate≤24 threads, successful FULL terminal gates, and the existing 90 GiB own-tree RSS watchdog. `docs/quadruped-log.md:35–49` describes the same operation. These are historical source records, not verification of the currently deployed host.

The archived `results/quadruped/scripts/run_job.sh:7–16,37–59` sets `RSS_LIMIT_KB=94371840`, samples the sum of `/proc/PID/status` VmRSS over discovered descendants every10 seconds, and initiates TERM then KILL on threshold breach. It does not use RLIMIT_AS. Its original source is not adequate custody proof: recursive `pgrep -P` traversal can miss reparented descendants, discovery and signaling race PID reuse, shared mappings can be counted multiple times, and allocations can overshoot between observations. The5-second grace period adds further interval exposure. Even the collected tree is not an atomic snapshot. The metadata correctly calls the quantity `peak_rss_kb_tree_sampled_10s` (`86–90`); retain that precision.

The audit's proposal B discusses RLIMIT_AS/cgroups but does not explicitly retain this monitor. **A per-process address-space cap is not a substitute for the historic RSS stop rule.** Root-supplied OS evidence establishes that RLIMIT_AS limits virtual address space per process, inherits across fork/exec, and can have its hard ceiling lowered by an ordinary user. It does not establish aggregate tree RSS, GPU memory, kernel charges, or reservation. `memory.max` requires actual delegated control and has its own accounting/transient behavior. No delegation fact is available here. Do not convert94371840 KiB into an RLIMIT_AS value merely because both are expressed in bytes.

Required decision: explicitly select the sampled policy as a fallible operational control, or retain the static model. If whole-tree physical containment is newly required, the sampled fallback cannot satisfy that requirement. The original research/global constraints and archived operation examined here do not themselves require such hard containment. Under their existing weaker semantics, an operational fallback is compatible in principle, provided supervision, capacity observations, and failure evidence are implemented honestly. This is an architecture inference, not a host certification.

The missing specification is the exact physical coordinate and attribution rule: allocator-owned bytes, summed RSS, cgroup charges and host MemAvailable are different quantities. Exact source/configuration identity is necessary but not sufficient to define how shared mappings, page cache, kernel objects and resident credit enter each comparison. ## 2. Recommended finite policy decision

Record the following together before source changes:

1. **Claim and metric.** The new path authorizes bounded registered work under observed capacity and a monitored stop rule. It asserts neither complete physical fit nor reservation nor hard RSS containment. Preserve90 GiB and the10-second sampling policy as existing operating values. Source-derived allocation sizes remain sizing/sanity evidence with explicit scope and unknown overhead, never universal physical upper bounds. A current capacity screen can reject a case when known necessary demand exceeds observed capacity; its passing is only an operational admission decision. Do not require an invented margin or require every unknown runtime allocation to become a proved physical term under this new policy.
2. **Controls before expansion.** Establish the same stable cooperative host lock and trusted origins before context, raw-input decoding, parameters or pool construction. Retain the SAME owner, bytes, selection, source identities and independent seed0/selected reconstructions through completion. Minimal trusted bootstrap/launcher work still has a finite bounded implementation and read caps, but must not claim its wire length is a physical envelope. Explicitly replace the old physical-proof prerequisite for this branch; otherwise the new policy remains vacuous.
3. **Closed supervision.** Select one reviewed ordinary-user per-job supervisor/worker arrangement, with one active registered worker and a closed set of provenance helpers. The supervisor must bind own child identities from spawn, retain safe signaling handles where available, track permitted descendants/reparenting, and refuse unknown child routes; a bare reused PID is never a kill target. Keep inherited same-description lock custody in worker/Python/Git until covered work ends. If the selected OS mechanism is unsupported, refuse that mechanism specifically. A monitor cannot be advertised as reliable tree supervision merely because the old shell script exists.
4. **Failure semantics.** Record sample scope/time and shared-page double-counting explicitly. A missed/invalid sample, lost supervision, unknown surviving child or identity mismatch makes the attempt incomplete and prevents advancing to another owned job while custody is unresolved. Stop only verified owned work. Keep monitoring alive independently of the scientific worker; worker loss can be recorded by the supervisor. Supervisor death is not guaranteed hard containment: inherited custody prevents a second cooperative admission, and surviving work requires exact later reconciliation. Do not classify an arbitrary signal as OOM without evidence. After durable start, allocation failure/watchdog/known OOM is failed or incomplete, never pre-start unmeasured skip. A worker killed before scientific final publication leaves no fabricated endpoint; the supervisor may publish a separately attributed linked terminal failure, never a fabricated scientific measurement.
5. **Other limits.** RLIMIT_AS may be added later as a separate explicitly dimensioned control after exact cap/virtual-mapping/thread/helper semantics are chosen. It is not necessary to make the initial sampled-policy branch implementable. Delegated cgroups are optional stronger controls only if actually available; no sudo/provisioning assumption. GPU VRAM needs its own actual device/pool evidence and failures. Disk/inode/quota observations, finite artifact counts and honest write failures remain required; host memory monitoring cannot cover them.

This policy can permit real computation rather than universally refusing missing physical proofs. It can also fail during execution; that is a property recorded by the original operation and already acknowledged by the static proposal's capacity-race language (`141,150,164`). Accepting it changes the strength of engineering admission evidence, not security, correctness, accuracy, algorithm, epochs, datasets or research comparison thresholds.

Rejected alternatives: leave every gate unavailable and call Task54 complete; assign zero to unknown physical components; multiply observed RSS by a margin and call it proof; impose the90 GiB value on virtual memory; depend on unobserved delegation; replace NI with interactive refresh; reduce registered scientific work; count OOM/SKIP as measured success. The cost of the selected change is a versioned resource evidence path, concrete supervision and lifecycle integration, compatibility tests and later bounded native validation. It avoids transitive physical proofs of all runtime/kernel memory while retaining explicit operational limitations.
