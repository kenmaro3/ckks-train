## Required corrections

### R1 — Close the pre-expansion claim's work identity and production order

Contract lines25,46,70,78 require the sampler/worker handshake and `claim.bin` before the first allocating context/registry/input expansion. Line70 makes `claim.work` the exact Train registration plus request. Line15 separately requires actual `RegisteredCases::select` to produce the canonical case bytes/digest rather than inventing them.

The existing route cannot provide that registered identity at this point: `study_runtime.rs:312-338` captures runtime, loads the verified current context, loads the registry and projects registered cases, then selects the case. `study_profile/registered_case.rs:238-252,376-395` confirms that selection borrows registry-derived objects whose canonical bytes are created during projection. A selector available in bounded CLI/bootstrap parsing is not that object. Moreover, `work:Bytes` has no specified selector-versus-canonical-registration discriminant or ordered grammar in this proposal.

If "registration" means canonical registered-case bytes, the claim depends on the expansion it is required to precede. If it means the requested selector, that interpretation and its later exact binding must be explicit. A source implementer should not silently resolve this by moving context/registry loading ahead of claim custody, trusting caller-provided case bytes, or manufacturing a registered capability from a selector.

**Required remedy:** make the pre-expansion claim carry a closed, bounded, non-authorizing requested-work record: Train selector plus compiled request/consumption, or the stated preparation operation/profile/explicit seeds. Specify that record's ordered encoding and bounds. After the live owner admits context and registry expansion, use the existing registry selection and bind the resulting exact registered case/request back to the retained claim before capability/admission/start construction. This can be a check retained in the resource sidecar/live owner; it need not add a daemon or mutable claim registry. Preserve pending/initial-sample/claim publication before expansion and retain no-clobber immutability. Alternatively specify another concrete bounded producer that meets all these requirements, rather than leaving the choice to implementation.

**Finite verification:** independently encoded requested-work positive Train/preparation vectors; mismatched selector, consumption, request and resolved case negatives; order trace proving claim durability before context/registry allocation; refusal before gates/start when resolved registration disagrees. These are source/order checks, not native custody evidence.

### R2 — Preserve the existing User/Resource overlap cross-check explicitly

Contract lines60,66 replace the old structured `Resource.claim` with a FileRef and enumerate Common/branch/consumed-plan/request equality checks for `CurrentEvidenceBundle`. The existing composition also enforces `selected AllowedScope.overlap == resource.claim.overlap` in `study_reference/document/evidence.rs:350-365`. This is an additional relation, not part of Common/branch/request equality. Its meanings are frozen in `task-54-d7-gate-schema-proposal.md:94,100`: serial0 versus explicit_overlap1, with an exact authorized scope tuple rather than a wildcard. The new `claim.bin`/`SupervisorBinding` fields contain no overlap field.

The chosen implementation is explicitly serial, so no new overlap mechanism is needed. Nevertheless the port must not drop this relation when it replaces the old bundle or infer a different authorization tuple merely because execution is conservative. The general statements that user constraints remain unchanged indicate the intended result, but the concrete replacement validator and test inventory do not close it.

**Required remedy:** define the new resource branch's overlap as the fixed semantic value serial0 and require the selected existing UserScope overlap to equal serial0 in `CurrentEvidenceBundle` and its live producer. No historical wire change is necessary. If represented on the new wire, fix its sole accepted tag rather than allowing caller choice. Add an explicit wrong-overlap negative for both Full and Quick while retaining revocation/hold/retry checks. Do not reinterpret explicit_overlap1 authorization as serial0 without an explicit separately reviewed rule.

## Seams that are adequately closed at proposal level

1. **Operating policy and finite process custody.** The root decision explicitly replaces the physical-proof prerequisite for this branch and preserves 94371840 KiB, ten-second sampled summed process RSS and five-second TERM grace. Source payloads are not relabeled RSS. A direct-child trampoline that waits before exec gives the supervisor a concrete interval to bind an unreaped child with pidfd; cached rustix pidfd/waitid APIs support the stated safe-handle approach at the API level. Command::spawn is not asserted to return a pidfd atomically. The contract prohibits pre-bind wait/reaping and PID-only kills, separates unregistered descendants from signalable owners, and treats unknown custody as unresolved. This is credible source architecture, not verification of kernel behavior.

2. **Inherited lock, helper routes and death.** fd0 lock custody is distinct from the duplex fd1 control stream; Git's explicit transition to bounded raw output avoids parsing its output as later IPC. Python/Git must become supervisor direct children through the broker, replacing the actual `context.rs:869-928` and `study_reference_build_support.py:800-851` subprocess paths. Existing helper behavior cannot be reused unchanged: it currently nulls stdin, writes raw stdout and launches/kills its own Git child. The proposal expressly calls for those changes and renewed build/source receipts. Nonblocking supervisor drain/sampling, worker loss, supervisor EOF, live inherited holders and durable cross-checkout pending markers have distinct consequences. The contract honestly leaves long HE/Git work after supervisor death and unknown children unresolved; it does not claim hard containment or authorize another user's process signals. Native no-descendant/FD/exec behavior is an explicit release prerequisite.

3. **Wire transition and provenance.** A separate observed-resource domain avoids changing old Requirements/22-component meanings. The four non-resource v1 records can remain unchanged; Full admission currently checks nonempty gate policy strings (`document/admission.rs:568`), while old Quick hardcodes the v1 tuple (`evidence/quick.rs:219-238`), justifying the explicit Quick v2 consumer. The new current bundle and exact tuple/replay rejection are required implementations, not capabilities conferred by decoding. Source/build/helper renewal and the same context/process/store owners are preserved. R2 is the remaining identified compatibility omission.

4. **Real CPU endpoint and NI separation.** The current continuation really drops session/client/evaluation and returns progress (`cpu_continuation.rs:186-315`); replacing that driver with a frame retaining them through evaluation is necessary. The proposed endpoint uses existing `CpuDiagonalSession::snapshot` and `StudyClient::inspect_snapshot` APIs. Inspection checks exact client/context/parameter association, finite W/b and counter isolation (`study_client.rs:711-753`); the snapshot itself clones encrypted model state (`study_diagonal.rs:517-523`), so the stated snapshot overlap sizing is material. The proposed real-class last-total-order argmax and finite padded logits match `study_plain.rs:375-398`. NI's diagnostic decryption is separate from training, with no refresh service or feedback into its updates. No successful final result may come from a checkpoint preceding poison/failure.

5. **Timing and FP32.** The corrected contract's cumulative server-step coordinate is compatible with Reference `EndpointFact.update_ns`: `study_reference/session.rs:318-350` charges the actual engine step, evaluates separately, then records cumulative update time. On the CPU path, input encryption precedes `session.step` (`cpu_continuation.rs:222-229`); it must remain outside the server-step timer as specified. Actual bootstrap/refresh calls are nested portions of that step, never added again. Paired FP32, snapshot/evaluation, setup and result publication are separately charged. Pipeline elapsed includes FP32 and is explicitly not the target-time field. The specified target threshold, scheduled first crossing and final-time right censoring avoid the prior FP32-inflated latency problem. Tests should assert these timer boundaries with injected deterministic durations; no measurement exists yet.

6. **Executable JSON, durable linkage and tables.** The canonical binary plus same-executable JSON/export, byte equality, worker end links and independently resolved supervisor closure form an acyclic publication order. The JSON contains actual endpoint fields and provenance rather than delegating scientific assembly to shell/Python. A preterminal export alone is insufficient for a completed table row; failed/killed workers do not yield invented scientific records. `run_all.sh` receives an actual serial two-invocation registered route; Quick remains two updates and excluded from science, Full retains target/reference and ten-seed denominators, and `paper_tables.py` remains authoritative with legacy FULL1/2 aggregation preserved. The fixed initial selectors are partial adapter coverage, not deletion of the 21-profile/Full2680+20+7/Quick268 matrix.
