## Decision

**Do not make exhaustive physical-memory proof of the whole Rust/glibc/Python/Git/kernel stack the only route to the original experiment runner.** Keep the existing source allocation work as sizing evidence, and propose a separately versioned operational resource-admission contract: source-derived workload sizes, actual capacity observations, enforceable limits with explicitly stated coverage, retained ownership, and truthful failure reporting. This changes a later engineering mechanism, not the numerical/scientific gates. It must not masquerade as completion of `d7-cpu-allocation-v1` or populate its physical byte fields with estimates.

The current static path is **not proved impossible**. Its Cheb recursion and report reference graph are finite. However, its accepted documentation does not yet specify a closed, achievable proof boundary for physical attribution, runtime/kernel residuals, errors and helper behavior. The existing materials therefore cannot establish that another sequence of worksheets will discharge the gate on the allowed host. This is a specification/implementation problem in addition to missing measurements.

No resource design can promise successful completion of every registered case on this shared host. The required deliverable is a full-scope runner and actual evidence, including honest failure/unmeasured rows; it is not a declaration that all rows fit. Nothing in this audit authorizes a server operation during FULL2, a new numeric budget, sudo/cloud use, or publication.

The physical accounting ambiguity matters concretely. Host MemAvailable, process RSS, allocator-owned bytes and cgroup charges are different quantities. The proposal already distinguishes measurements (`41–42,125`) but Requirements offers one host total/incremental total. Kernel file/page-cache and shared mapping charges cannot be assigned consistently merely by giving them component21. The profile must define which quantity the source bound majorizes, how its terms correspond to each capacity comparison, and how already charged/shared resources are treated. Conservatively counting all potentially incremental resources can be sound, but only after that mapping is stated; it may also reject every real case.

Finite work can give extremely loose bounds: charge every allocation request over all bounded updates and never credit frees, with exact allocator/runtime envelopes. That avoids some liveness complexity but could exceed machine capacity by orders of work repetition. This audit does not calculate that bound or assert it fits. It explains why “finite” and “practical admission evidence” are separate questions.

Likewise, no source proof can stop unrelated users consuming RAM after an observation. The selected design already concedes this and classifies later OOM as failure (proposal141,150,164). Universal physical-fit or no-OOM language would exceed the **current** design, not only the proposed alternative.

## 3. Alternatives and recommended contract

### A. Complete the current static physical model

Retain as an optional stronger admission mode if root chooses to pay its cost. First close the metric/attribution contract, freeze serial/parallel and helper domains, implement final allocation-producing integration without enabling positive gates, and derive std/allocator/kernel envelopes against that source/build/environment. Then independently admit and execute bounded validation; only accepted complete evidence may construct the existing Resource capability.

Advantages: retains current schema semantics and provides a reviewed bound for the stated supported environment. Costs: transitive proofs for dependencies and host profiles, repeated renewal on source/environment changes, potentially unusably conservative bounds, separate GPU/external models still necessary. Neither Cargo.lock nor a Linux compile establishes actual loaded identities/configuration. No evidence here shows the host cannot furnish the needed source/configuration; equally, none shows it can. The next proof unit would need to close the environment/metric contract before another primitive worksheet—not assert impossibility from unfinished terms.

### B. Operational admission with enforced limits (recommended design direction)

Define a new contract that claims **bounded execution under named controls and observed capacity**, not “complete physical upper bound” or “guaranteed fit.” Retain source sizing for raw/decoded/prepared owners and cryptographic work; report unexplained runtime overhead and observed peaks honestly. Source sizing and measurements cannot themselves become physical proofs.

Separate enforceable domains:

* An ordinary-user lowered hard address-space limit can constrain that process's future virtual mappings, including allocator mappings. It is not an RSS/physical-RAM limit, not a GPU-memory limit, not an aggregate parent-plus-children limit, and not coverage for all kernel charges. It may cause allocation failure/abort and interfere with thread/device mappings; those are explicit validation cases. Hard-limit inheritance must be checked for every controlled child and an upper bound on concurrent descendants derived. Do not treat a per-process limit as a whole-tree budget.
* If the account already has suitable delegated cgroup-v2 control, a dedicated non-escapable controlled workload subtree can enforce the configured memory accounting limit across descendants. Validate membership, ancestry, permission boundaries, swap behavior, kill/failure records and the supported kernel accounting semantics. A memory controller is neither RAM reservation nor perfect isolation from host OOM; transient behavior and charges outside its scope must be stated. Do not assume delegation exists, change another user's group, or request privileged provisioning as part of this task.
* Neither mechanism establishes GPU VRAM safety. GPU routes need separately validated device/pool allocation behavior and current device-capacity evidence. A consumer GPU's available-memory snapshot cannot reserve VRAM against unrelated work.

These are candidate mechanisms, **not host observations or a completed low-level OS design**. Exact supported-version semantics and APIs must be checked in the later bounded implementation/native work. This read-only audit performed no web/host validation. It would be wrong to certify physical containment from RLIMIT_AS alone, or to offer delegated cgroups as an already available solution.

For an account without delegation, the finite alternative is an explicitly narrower operational contract: closed trusted processes, inherited per-process hard limits, bounded child concurrency, source sizing, actual host/ancestor observations and no physical-reservation claim. Root must explicitly decide whether that contract meets the original shared-host operating constraints. If a **whole-tree physical-memory cap** is required, this fallback does not satisfy it; report the exact missing mechanism and retain refusal. Do not manufacture a pass merely to make the runner execute.

No numeric cap is proposed here. Limits must be selected from the actual permitted workload/resource policy and fresh host facts, documented in their own units, and validated against the relevant runtime. A small arbitrary limit can cause universal failure; a guessed fraction of free RAM is not a proof. Empirical calibration informs feasibility and future policy choices without becoming an upper-bound theorem.

### Rejected substitutions

Multiplying a measured peak by a margin, relabeling logical payload as RSS, relying on cooperative flock to reserve memory, silently omitting unknown components, leaving all entrypoints refused and declaring Task54 complete, shrinking epochs/model dimensions to force a row to fit, or marking post-start OOM as an unmeasured pre-start skip are rejected. Rewriting provenance into a daemon/custom allocator solely to avoid helper proofs adds substantial unrelated work and still does not bound GPU/kernel behavior.

### Compatibility and claims requiring changes

The current `d7-cpu-allocation-v1`22-component physical semantics must remain interpretable as historical evidence. Do **not** stuff new limits/estimates into `Requirements.peak_host_bytes`/`incremental_host_bytes` or leave unknown components zero. Introduce a distinct reviewed resource-policy identity and explicit versioned evidence record; retain a private Resource capability but let its constructor require the exact accepted contract and actual live controls. The existing five-capability API boundary can remain; its accepted policy semantics cannot be changed silently.

Outer envelopes might stay byte-compatible by referring to a new evidence domain, but existing closed codecs/policy matching may require a deliberate wire revision. Resolve this in the concrete source brief, with old-domain refusal and cross-policy replay vectors. This audit does not assert compatibility without inspection of every consumer. Required changes include policy/oracle/reader/constructor integration, source/build provenance renewal and independent review; those costs replace rather than conceal the static-proof cost.

Rename/remove new-path claims of “complete applicable physical model,” “physical requirement,” and “fit proved.” Use “source-sized workload,” “configured enforced address-space/cgroup limit,” “capacity observed,” and metric-specific measured peaks. Keep actual numerical/KAT/security/applicability evidence, Full target/threshold binding, before-allocation custody, exact retained inputs and attempt durability unchanged.
