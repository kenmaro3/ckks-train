# Historical correctness source applicability review

## Decision and scope

The rename-aware comparisons support **qualified source continuity for the old M1 KAT's directly exercised arithmetic and for the legacy FULL1 CPU NI route**. They do not establish complete executable equivalence or a current implementation-gate PASS. Neither historical result should be discarded merely because crate names changed; neither should be expanded to cover newly introduced operations, dispatch choices, parameters or routes.

This is a prerequisite evidence analysis, not a review of the concurrent admission/correctness codec work. Comparison target is committed `263c830e3568ccfa4bbec6bc746c08a4971aa197` throughout. Historical sources are M1 `37f9502281576edb96afde41f42843f6d917161f` and FULL1 producer `ff2c2ebc9d7946490bcf63f8b6be9f45fe67d49f`. Current worktree source was not used as the comparison target. No Cargo, tests, test listing, HE, native execution, SSH, source edit, commit or subagent was used.

Read inputs: `task-54-d7-correctness-source-comparison.md`, `task-54-d7-existing-correctness-evidence-map.md`, the two complete retained diff packages and path/hash JSON, relevant pinned original/current source, pinned `docs/m1-report.md` §§2–3/5, `docs/bootstrap.md` §§11.4–11.6, and FULL1 retained README/meta/result plus the historical producer's relevant dispatch. The latter dispatch inspection is contextual and does not enlarge the comparison to a whole bench/executable audit. Review concentrates on substantive hunks affecting the named CPU paths; it is not an audit of every newly added module or unrelated test.

## M1: exactly what the KAT established

`ckks/tests/seal_kat.rs` is rename-only. Its `seal_to_hekit` and `hekit_to_seal` tests import SEAL secret/public keys and construct an evaluator without our relinearization/Galois keys. The first direction imports eight SEAL ciphertexts, checks round-trip serialization and exact decrypted polynomial limbs, and directly exercises our `add`, `mul_no_relin` and `rescale`. The reverse direction emits six outputs: symmetric encryption at two levels, encryption with SEAL's public key, addition, a three-component product, and rescaling SEAL's product. External SEAL verification checks the reverse direction's error bounds.

**Loading SEAL-produced relinearized or rotated ciphertexts does not execute our relinearization/key-switch/rotation implementation.** This KAT does not exercise our key generator, SSE, bootstrapping, n16_train hybrid decomposition, or a neural-training route. The independent M1 precision checks supply different coverage and must remain a separate evidence clause.

The original criteria remain exactly those documented in M1: bit-exact SEAL-to-hekit polynomial/arithmetic comparisons, with the documented floating decode difference at scale 2^80; reverse interoperability is bounded-error, not bit-exact. Secondary maximum-slot error bounds are 2^-25 for symmetric/add/tensor/relinearized SEAL objects, 2^-23 for public-key/rescale, and 2^-15 for the SEAL rotation. Our centered rotation intentionally is not bit-identical to SEAL's noncentered rotation. No uniform replacement threshold is justified.

`docs/m1-report.md` documents two successful local bidirectional script runs, most recently at 37f9502 with `PASS: 0 failure(s)`. This remains historical evidence. The ignored KAT fixture directory is regenerated on each run, so present fixture bytes alone do not establish which historical invocation consumed them. Moreover, `kat_dir()` permits the ignored Rust tests to return early if fixtures are absent. A bare harness PASS is therefore insufficient proof of an exercised KAT; evidence used for an executable gate must establish actual vectors/non-skip and the reverse SEAL verification, as well as its source/config lineage. This finding does not authorize a rerun.

## FULL1: actual legacy NI route and changed dependencies

The retained FULL1 record is a real historical seed-0 NI result, with recorded exit 0 and no watchdog firing. Its producer is ff2c2eb, recorded clean. The command used noninteractive, faithful, when-needed placement, transpose reuse, batch 64, an explicit schedule/initialization/dataset/index set, one flattened epoch and the historical schedule-batch argument. The route was 196->32 (`z²+z`)->16 (linear), MSE, NI NAG with frozen-zero biases, n16_boot, diagonal layout d=256/B=64, one physical 64-lane microbatch, 750 updates/48000 samples. The recorded Linux parallel run used 12 threads. Accuracy 0.9036 versus the paired B64 float 0.9037 remains that run's observation; FULL2's designated ReBoot seed-0 accuracy gate is separate.

Historical `bench/src/bin/mnist.rs` dispatch constructs the Bootstrapper before later public/relinearization/Galois keys, uses the default evaluator and `NonInteractiveTrainer`, selects NI NAG, transpose reuse and frozen biases, and calls `train_step_valid`. This matters: interpreting an unrelated interactive NAG change as a change to the FULL1 optimizer would be incorrect. Conversely, present D7 constructor order and retained inputs are not proved identical by these old lines. The retrieved binary hash is not by itself an original complete build attestation.

### Original bootstrap criteria remain separate

`docs/bootstrap.md` §§11.4–11.6 define secure n16_boot, N=65536/all 32768 slots, message range [-1,1], and >=16 bits by maximum absolute error. The documented dense result is 17.46 bits; the additional 17.41-bit seed is an observation. The miniature 26.77-bit result and the |message|=4 experiment do not replace that criterion. Existing parameters and BootParams remain unchanged in this comparison, including SSE ephemeral weight 32 and default K=13/degree=127/r=0; expected output level is 16, then 15 after unpack.

The unchanged-normalized secure trainer test `n16_boot_keys_three_updates` is a separate declared criterion: 16->16->4 with both activations Relu2, B=32, dedicated transpose, AfterUpdate, three updates, weight error <=1/256 and bootstrap count `2 * boot_count * 3`. This is not FULL1's B64/when-needed/reuse/linear-output route. Its source declaration is not a new executed pass. FULL1 final accuracy is not an independent full-slot bootstrap precision measurement, and a bootstrap precision result alone is not a full NI training correctness trace.

## Actionable evidence decisions and missing proof

1. **Keep four evidence claims separate:** M1 SEAL interoperability/direct arithmetic, M1 basic precision, secure-n16 bootstrap/three-update criteria, and legacy FULL1 route outcome. Preserve each original threshold, precondition and documented exception. Do not promote an imported SEAL relin/rotation object into a test of our key-switch implementation, or legacy accuracy into bootstrap precision.
2. **Use this review as a bounded source-applicability supplement.** It resolves the misleading all-new appearance caused by renamed paths and identifies relevant arithmetic continuity. A consumer still needs to bind the actual retained parameters, mode/backend/configuration, key roles and constructor order, layout/transpose, activation/loss/optimizer, schedules, initialization and inputs to the claimed historical coverage. For a different route or new dispatch branch, this comparison supplies no positive applicability by itself.
3. **Close evidence lineage at the correct boundary.** If historical KAT/precision is to satisfy a machine-consumed prerequisite, locate the original exercised result/non-skip/reverse-verifier evidence and applicable source/config lineage; documentation and current fixture bytes alone are insufficient. For a complete current executable claim, the omitted driver/build/dependency/toolchain/native/generated boundary must have its own reviewed linkage. The present package does not supply it. This is a concrete missing proof, not a declaration that all such records are absent everywhere.
4. **Retain MissingApplicability where the link is missing.** Do not fabricate current-source authority, a D7 Started record or new admission/start/lock bindings for FULL1. P4/P5 or other existing evidence may independently cover a new route, but they were not re-audited in this task. No automatic all-profile rerun, new numeric threshold, new test filter or execution release is established here.

No arithmetic defect requiring source correction was identified in the inspected continuity paths. The principal limitation is evidentiary scope: source continuity supports a specific historical result's relevance, while actual route/build custody and the original result must still be bound. Original C/R/A, full matrix, baseline, GPU/security/resource requirements, gates and holds remain unchanged. This report grants no broad prerequisite PASS or live authority.
