## Findings

### Q01 — Important: an inheritable duplicate of M's control socket is leaked into L, preventing the required M EOF

**Location:** `crates/ckks-train-bench/src/study_supervisor/handshake.rs:186–188`; reachable through `probe_adoption.rs:220–232`, with the blocking consequence at `probe_adoption.rs:849–893`.

`child_channel` duplicates fd1 using `rustix::io::dup` and stores that duplicate in the long-lived `Channel`. This duplicate does not have close-on-exec set. This is not an inference from a wrapper name: the installed, pinned rustix 1.1.6 implementation documentation at `src/io/dup.rs:10–14` explicitly states that `dup` does not set `O_CLOEXEC` and points to `fcntl_dupfd_cloexec` for that behavior. The fd0 duplicate on the preceding line has the same flag issue.

**Concrete trigger and trace:** invoke either existing native nested check, `subreaper-known-unknown` or `parent-eof-custody`. M first authenticates its P–M channel, retaining the inheritable fd1 duplicate. M then calls `OwnedChild::spawn` for L. The new child's standard fd1 is replaced with the M–L socket, but `Command` does not close arbitrary unrelated inheritable descriptors: L also inherits M's duplicate of the old P–M endpoint. No source path closes that inherited extra descriptor in L. The ancillary transfer's `CMSG_CLOEXEC` flag does not repair this ordinary inherited descriptor.

After the custody acknowledgement M exits. P requires M's terminal status **and** stderr EOF **and** control EOF before reaping M and advancing to adoption/leaf shutdown (`probe_adoption.rs:868`). L's extra P–M endpoint prevents that control EOF while L remains alive. In check1 L intentionally stays alive waiting for P's later TERM (`:462–467`); in check6 L reports original-parent EOF on rescue and then waits for P's later rescue Stop (`:455–459`). P reaches neither action while waiting for M EOF. The 60-second failure paths eventually intervene; they do not produce the intended successful adoption/EOF measurement. This is a source-level descriptor-lifetime defect in both native scenarios, not a claim that either scenario was executed here.

**Minimum remedy:** make the private duplicates close-on-exec at acquisition, preferably atomically with the existing safe `fcntl_dupfd_cloexec` API (or an equivalent safe CLOEXEC duplication). Keep the intentionally inherited standard fd0/fd1 and the SAME lock OFD semantics. Audit other private descriptor aliases across the fixed P→M→L boundary; do not relax the actual EOF requirement or treat M status alone as proof of drain. Add a narrow check of the actual duplication helper's FD flags, and retain a future native assertion that P observes M EOF while L is still alive and before L Stop/TERM. Projection/count-only tests cannot detect this leak.

### Q02 — Important: clean framed EOF from a live child never triggers production failure/cleanup

**Location:** `crates/ckks-train-bench/src/study_supervisor/monitor.rs:514–535`, consumed by `controller.rs:355–365`; compare the manually initiated native fault cleanup at `probe_driver.rs:897–919`.

`Channel::turn` correctly rejects a truncated frame but treats EOF on a frame boundary as `eof=true` with no frame/error (`protocol.rs:353–373`). `Monitor::pump` only copies this into `drain.stdout_eof`. Its sole lifecycle notification is `Message::Exited`, emitted only when terminal status and both EOFs are present. There is no separate control-loss notification or stop transition when the framed channel reaches clean EOF while the acquired pidfd still reports a live child.

**Concrete trigger and effect:** an authenticated worker or Python trampoline/helper loses/closes its framed control channel after a complete frame while remaining alive, with no queued supervisor write. This is precisely the live-child/closed-channel state that the existing native check3 source can inject. In the production controller, `pump` returns no failure and no exit, `scheduler.reason()` stays `None`, and `run` keeps sampling/waiting. Even when both outputs are closed, the owned process and any known helpers are not stopped. A normal RSS value does not make the lost control protocol usable. The attempt can remain stuck until an unrelated RSS, timing, storage or external failure; the production controller has no native-style 60-second validity timeout. No false successful closure is required for this to be a correctness failure: the specified control-loss stop is simply not initiated.

The native closed-stream case does not cover this production decision. It observes both EOFs with a live pidfd, manually queues Stop, and explicitly calls `monitor.fail(ProtocolFailure)` at `probe_driver.rs:919`. That tests the stopping wait/drain once failure has already been supplied by the harness, not automatic detection by the running supervisor. The pure `DrainState` test likewise verifies that EOF is not exit, but does not verify that control loss initiates stopping.

**Minimum remedy:** distinguish framed control loss from successful drained completion in the real pump/controller path, and route unexpected clean EOF into the existing owned-child TERM/grace/KILL cleanup. Preserve terminal-status/required-EOF/reap checks; EOF must never be treated as exit or permission to discard custody. Preserve the separate Git raw-output transition and explicitly allowed terminal protocol phases rather than indiscriminately failing every raw EOF. Add a covering test that passes a live-child clean-EOF observation through the actual shared failure decision and asserts the stop transition without manually calling `fail`; keep the native both-EOF/queued-output test as a separate wait/drain check.

No additional Minor finding is raised. These findings do not request an architecture rewrite, a new native selector, or a relaxation of any custody/evidence gate.
