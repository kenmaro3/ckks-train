## 2. Geometry choice: reuse the existing candidate wrapper at canonical preparation

**Preferred canonical choice needs no production P3 geometry-retention change.** Inside private client preparation, first call `validate_plan_binding` on the real immutable MaterializedProfile/RegisteredCase/plan/actual parameters and the exact request. Then call existing `describe_candidate(materialized.metadata(), registered, params, request)` once. Reject `issue()!=None`, require exactly one geometry, take its typed `StageGeometry` through `geometries()[0]`, and compare its logical training/bootstrap manifest to `plan.keys()`. This rebuilds geometry through existing `checked_mode -> make_stages -> plan_stage_geometry`, not an independent planner implementation or a whole update-schedule rerun.

Important limits: describe_candidate calls `make_stages` with descriptive lr/reference.08/.08. **Never use its initial_states as schedule state or actual optimizer basis.** Runtime initial/before/after labels and coefficients come only from the canonical plan. Its input_status/unproved fields are not admission, and a successful candidate is not a session permit. Geometry/activation/transpose/layout are deterministic from the same trusted immutable metadata plus binding-revalidated request/parameters; do not pass a caller-edited ProfileMetadata. Descriptive geometry is a derived setup value, not an independently accepted registration.

This costs one extra geometry and one extra initial-state P2 call for the one stage, zero update/handoff calls and zero key/HE constructors. `describe_candidate` does not charge Work::Wrapper but its make_stages charges Geometry/Initial on the supplied `PlanningBudget`. Budget **limits are bound in encode_request**, so the original canonical request must reserve this setup allowance before plan construction; do not increase its limits after hashing. Preserve exact errors if allowance is exhausted. The mini synthetic HE tests cannot use this canonical wrapper: secure_parameters deliberately rejects their parameters.

Keep the returned CandidateDescription in the **client-owned preparation frame** while constructing/checking Mlp/compact state. Borrow its geometry there. If session needs owned geometry for ongoing metadata checks, clone only this one StageGeometry once into the bridge's private prepared evaluation description, then drop candidate's placeholder states; no geometry clone inside Arc<DiagonalPlan>, and no mutable candidate/materializer inside session. Its nested geometry allocation/liveness belongs to subsequent bridge resource accounting, not an altered P3 receipt-byte claim. Existing trainer compact_layout/MLP dims plus plan summaries are enough for ordinary per-step checks, so storing full geometry in session is avoidable.

Alternative if root later needs allocation-free transfer: a narrow crate-private `CandidateDescription::into_geometries(self)` can move existing owned geometries, dropping descriptive states/manifest. It avoids the clone but is not needed for correctness. Do **not** retain every StageGeometry in DiagonalPlan merely for P4. Such a retention amendment would require charging outer StageGeometry storage plus internal identity dims/activation/reuse-pool vectors, shapes, optional compact plans/containers/bias slots, nested transpose recipes/chains, keys and masks before retention, with plan Arc extending all those lifetimes. The present choice avoids that amendment and a new retained-payload model entirely.
