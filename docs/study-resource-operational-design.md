# 実容量の観測とRSS監視に基づくCPU実行設計

2026-11-08、設計として採用。rootは[FIX2契約と独立レビュー](../results/validation/task54-d7-cpu-integration-design/README.md)を読み、R1/R2と内部呼び出しの修正を確認した。コード・実機・科学結果の合格ではない。

Task54の最初の接続対象は、登録済みIris/eMLP-1/seed0のCPU対話・非対話である。run_all.shから実学習、最終モデルの復号評価、FP32比較、実行ファイルが生成するprovenance付きJSON、表生成までを接続する。Quickは既定の2更新、Fullは既定の全更新と独立Reference/Targetを維持する。この2経路は最初の実装範囲であり、残りのモデル・GPU・ベースライン・10seedを削除しない。

設計変更の理由は、従来の物理メモリ証明がallocator/runtime/kernel等の会計境界まで未定義で、原研究計画より広い前提になっていたことにある。再帰処理や参照グラフが不可能という判断ではない。代替は、会計境界と環境を固定したうえで静的証明を完成すること、別途検証した仮想アドレス上限を追加すること、利用可能と確認できたcgroup制御を使うことである。今回は既存運用の94371840KiB（90GiB）・10秒間隔の自分の処理群のRSS監視を、新しい別versionの実行条件として採用する。推定値や未知の項を旧形式の物理上限へ入れない。

この方式は容量の観測と停止規則であり、RAMの予約や厳密な物理上限を保証しない。監視間隔中の超過、共有pageの重複計上、監視役の喪失などを記録し、開始後の失敗を未計測skipや科学的成功に変えない。90GiBをRLIMIT_ASへ読み替えず、cgroupの委譲権限も仮定しない。設計判断を誤れば共有サーバーへの負荷や測定の無効化につながるため、起動した処理だけの追跡・停止と後日の限定実機検証を必要とする。

監視役が起動したworker/Python/Gitを直接管理し、pidfdに結び付けた自分の処理だけを停止する。入力展開前から同じ協調ロックと入力の所有者を保持する。展開前の要求記録は実験の登録完了を意味せず、実際のregistry選択後に要求との一致を検査する。新Resource方式の逐次実行と既存UserScopeの認可値の一致も検査する。従来の静的Resource形式は履歴として読み取り可能なまま残す。

科学用JSONは学習実行ファイルが生成し、元の内部バイナリ形式記録、入力・実行開始・証拠・終了記録に結び付ける。Pythonは表を生成するが科学用JSONを組み立てない。最終モデルとclientの所有権を評価まで保持し、NIの学習へ復号結果を戻さない。time-to-targetは累積update時間に限定し、FP32比較・準備・診断・出力時間とは分ける。全処理の経過時間は別の指標である。

設計の合格と、コード・実機・科学結果の合格は別である。新versionのbuild/証拠、入力保持と実行入口の接続、監視とpublisherのLinux検証、実際のQuick I/NI、残りの全adapterは未完了。サーバーでの新しい検証はFULL-2と既存queueの順序を守り、独立した依頼で行う。数値・暗号学的な合格条件は変更しない。

この新しい経路では、[従来設計](study-resource-design.md)§2の全22区分の物理上限証明を実行前提にしない。旧Resource/Requirementsを再解釈せず、新しい`d7-resource-observed-rss-v1`と専用証拠を使う。既存の4種の非Resource検査、入力・owner・Full/Quick・Target・durable startの条件は保持する。Fullの汎用形式は維持し、Quickは明示的にv2へ分ける。詳細の形式と互換性は採用したFIX2契約を正とする。

実装は、独立した期待値と形式処理、監視とhelper、同じ入力の保持と実行開始条件、最終評価・JSON・run_all・表生成の順でレビュー可能な変更に分ける。最初の形式処理だけで完了とはせず、この接続を最後まで実装する。
