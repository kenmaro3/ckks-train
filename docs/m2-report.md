## 2. RQ1 の判定(Step 2)

研究計画 §4.3.2 の合格条件は 2 つ。(a) ReBoot と同一の N・セキュリティ・モデル構成・精度(±0.5 pt)で、1 サンプル・1 epoch あたりの鍵切替(回転 + ct-ct 乗算 + ブートストラップの鍵切替換算)が 30% 以上少ないこと。(b) 同一 CPU での wall-clock が ReBoot 公式コードより悪くないこと。

### 2.1 鍵切替(30% 以上少ない = 比 ≤ 0.70)

| hekit 側(B = 32 実測、ほかは注記) | 相手 | 比 |
|---|---|---|
| 19.78(回転 + relin) | ReBoot 37(M0 のコストモデル) | **0.535** |
| 19.78 | ReBoot レイアウト PerSample 37(実測) | **0.535** |
| 19.78 | ReBoot レイアウト Lazy 35.06(実測) | **0.564** |
| 字義どおり: 回転 + ct-ct 乗算 = 17.84 + 3.56 = 21.41 | ReBoot レイアウト 30 + 7 = 37(Lazy も PerSample も、ct-ct 乗算は 7 / サンプル) | 0.579 |
| バイアス勾配を除く: 613 / 32 = 19.16 | 37 / 35.06 | 0.518 / 0.546 |
| Dedicated 転置: 621 / 32 = 19.41 | 37 / 35.06 | 0.525 / 0.553 |
| B = 48 の式(2 暗号文、走らせていない): 14.4 / 15.4(暗号文をまたぐ遅延 relin あり / なし) | 37 / 35.06 | 0.39 / 0.42(37 に対して)、0.41 / 0.44(35.06 に対して) |

- **対話版の指標では合格**。いちばん厳しい比べ方(Lazy の実測 35.06)で 0.564、余裕は 0.136。字義どおりの指標(回転 + ct-ct 乗算)でも 0.579。
- **バイアス勾配の +20 KS / 更新(0.625 / サンプル)は hekit 側だけに数えている**。ReBoot 側はコストモデルにも Task 33 のレイアウトにもバイアスが無い。比は hekit に不利な側に倒れている。
- **ReBoot 側のモデル値 37 は、同じライブラリの上で実測と一致した**(PerSample、8 バッチすべて 30 回転 + 7 relin)。ReBoot の鍵切替数をモデルで置いたことによる誤差は、少なくともレイアウトの再実装の範囲では無い。ReBoot 公式コードの回数は数えていない。
- **M0 の見積もりからの推移**(0.222 → B = 48 の式で約 0.39 → B = 32 の実測 0.535)と、生のコストモデルが ×1.81 の過小予測だったことは §4「RQ1 への含意」と「コストモデルとの比較」に書いた。ここでは繰り返さない。
- **ブートストラップ込みの spec の指標は M2 では決まらない**。M0 のモデル(R Task 6)では、B = 32 で KS_spec の比は 0.87(不合格)、B = 64(2 暗号文)で 0.64、B = 48 で 0.74(不合格)。M2 で対話版モデルの省略(サーバ側の複製など)が見つかったので、非対話版のモデル値も M3 の実測で確かめる必要がある。

### 2.2 wall-clock(同一 CPU で ReBoot 公式以下)

同じ CPU(M3 Pro、1 スレッド)での、hekit の 2 つのレイアウトの比較。

| 比べ方 | diag hekit | ReBoot レイアウト Lazy | 比 |
|---|---|---|---|
| 実測の合計(クライアント込み) | 5004 s | 10261 s | 0.488 |
| 中央値 × 32(クライアント込み) | 4963 s | 8986 s | 0.552 |
| 中央値 × 32(サーバのみ) | 4301 s | 8838 s | 0.487 |
| hekit の実測合計 / ReBoot レイアウトの中央値 × 32(サーバ) | 5004 s | 8838 s | 0.566 |

- PerSample(外挿)に対しては、サーバのみで 4301 / 9790 = 0.439、クライアント込みで 4963 / 9944 = 0.499。
- 鍵切替 1 回あたりのサーバ時間は、diag hekit 134.4 s / 633 = 0.212 s、Lazy 276.2 s / 1122 = 0.246 s。時間の比(0.487)が鍵切替の比(0.564)より小さいのはこの差のためだが、その原因(鍵切替を行うレベル、ct-pt 乗算や rescale の数の違いなど)は切り分けていない。
- 注意点:
  - クライアント側の仕事が違う。diag hekit の refresh は 98 暗号文の復号と再暗号化(21 s / バッチ)で、NAG はサーバが暗号文で計算する。ReBoot レイアウトは dW の復号、平文の NAG、W の再暗号化(約 4.6 s / バッチ)。
  - 2 つの走行は時刻が違い、load も違う(diag hekit は 1 分平均 2.26〜5.34、Lazy は 2.62〜11.52)。中央値 × 32 はその影響を減らすための値で、外れたバッチは表 §1 に挙げた。
  - ReBoot レイアウトの JSON の `provenance` によれば、Lazy の最初のバッチは 266〜268 s(32 バッチで約 8540 s)で、中央値 × 32 の 8838 s にも load の影響が残っている。この値を使うとサーバのみの比は 4301 / 8540 = 0.504。PerSample の外挿も load で大きめに出ている可能性がある(同じ注記)。
- **これは §4.3.2 の基準ではない**。基準の相手は ReBoot 公式コード(OpenFHE、12 スレッドの OpenMP、ブートストラップ付きの非対話学習)である。
  - ReBoot 公式は、この Mac(36 GB)では CKKS コンテキストだけで 44 GB を超え、学習の最初の重みブートストラップで落ちる(Task 5、R)。
  - quadruped-gpu(RAM 123 GB)なら、論文のピーク 76 GB からみてメモリには載る見込みだが、このセッションではリモートへの書き込みが許可されていない。本人が回すセッション待ち。
  - 「同一 CPU」には hekit 側もその CPU で走らせる必要がある。スレッド数(ReBoot は 12 スレッド、hekit は 1 スレッド)の揃え方も決まっていない。
  - しかも ReBoot 公式はブートストラップ付きの非対話学習なので、意味のある比較の相手は M3 の非対話版の hekit になる。
- **したがって wall-clock の基準は未評価**。同じライブラリの上での比較(0.49〜0.57)は、レイアウトの差が時間にも出ることを示すだけで、基準の代わりにはしていない。

### 2.3 その他の条件(同一 N・セキュリティ・モデル構成・精度)

- **N**: eMLP-1 の 4 行(diag hekit、ReBoot レイアウト 2 行、ReBoot 公式)はすべて 2^16 で同一。
- **セキュリティ**: n16_train は BDGL16(HE Standard の BKZ.sieve と同じ式)で 143.9 bit、MATZOV で 141.2 bit。Core-SVP では 107.7 bit で 128 に届かない(M1 §4)。秘密鍵は一様な三値で、ReBoot 公式は疎な三値(h = 192)。§4.3.3 の「スパース秘密鍵を使うなら両者同条件」は、M2 では揃っていない。ブートストラップ用の秘密鍵とその安全性は M3 の扱い(`docs/bootstrap.md`、`docs/security.md`)で、本報告では評価していない。
- **モデル構成**: 層幅・活性化(z² + z)・損失(MSE)・NAG(lr 0.001、μ 0.9)は ReBoot eMLP-1 と同じ。違いは B(32 対 48)、weight decay(適用していない)、バイアス(hekit は SGD、ReBoot レイアウトの行には無い)。
- **精度(±0.5 pt)**: 未評価。M2 の走行は 1024 件 1 epoch の subset で、暗号化側と平文の双子が一致することの確認が目的。ReBoot の 94.61 % は論文 Table 4 の平文の双子による値で、M2 の subset とは学習量がまったく違う。

### 2.4 Plan B の選択肢(判断は本人に返す)

wall-clock の基準と精度の条件が未評価で、spec の指標(ブートストラップ込み)は M3 待ちなので、選択肢を並べる。どれを選ぶかは決めていない。

- **A. 判定を M3 まで延ばす**: Plan B は今は発動しない。M3 の非対話版(ブートストラップ込み)で spec の指標を測り、同じ時期に ReBoot 公式を quadruped-gpu で計測して、hekit も同じ CPU で走らせる。必要なもの: 本人が回す quadruped-gpu のセッション、スレッド数の取り決め。
- **B. 大メモリの CPU ホストを借りる**: ReBoot 公式と hekit を同じ CPU で走らせる。M0 §3 の見積もりは r7i.8xlarge(32 vCPU / 256 GiB)で約 $20〜65。課金を伴うので本人の判断。
- **C. wall-clock の基準を読み替える**: 相手を「同じライブラリ・同じ CPU 上の ReBoot レイアウトの再実装」にする(M2 の実測で 0.49〜0.57)。ReBoot 公式コードとは比べないことを論文に明記する。査読で公式コードとの比較を求められる可能性は残る。
- **D. 計画 §4.3.2 の Plan B を発動する**: 論文の主軸を「GPU 実装 + MIT スタック + 2020 年手法の再評価(どこで負けるかの分析)」に変え、RQ1 は「コストモデルと同一ライブラリ上の実測による比較」として残す。投稿先は WAHC のまま。

A〜C は組み合わせられる(たとえば A と C を両方とる)。

## 3. Iris

2020 年論文(Mihara et al., arXiv:2012.13552)の Iris 設定を hekit で再現した。バイナリは `crates/hekit-bench/src/bin/iris.rs`、結果は `results/iris_1_timing.json`(batch 1 の反復時間)と `results/iris_20.json`(batch 20 の 400 epoch 学習)。

### 設定

- **ネットワーク**: 4-10-3 MLP、バイアス付き。両層の後に Square。損失は MSE(3 出力で平均、標本でも平均)。SGD、lr 0.1。論文と M0 の SEAL 再現(`spikes/seal-2020`、`spikes/RESULTS.md` "Task 4")に合わせた。
- **損失の定数**: trainer の損失勾配は `a - y`(`hekit_nn::loss::Mse`)なので、`2 / d_out` を学習率に畳み込んだ。暗号化側の optimizer には `lr_eff = 0.1 · 2/3` を渡す。更新は M0 の `sgd_step` の `W -= lr · dL/dW` と同じになる。
- **データ・分割・前処理**: M0 スパイクと同じものを使った。
  - `crates/hekit-bench/data/iris.csv` はスパイクのファイル(UCI Iris、CC BY 4.0、scikit-learn 同梱版。出典は README)。
  - `crates/hekit-bench/data/iris_split_seed2020.txt` はスパイクの既定シード 2020 の 80:20 分割(120 / 30)。スパイクの `split_80_20`(`std::mt19937_64`)を書き出したもの。
  - 入力は学習データの平均と母標準偏差で z-score 化した。
  - 初期値は N(0, 0.2²)(重みとバイアス)。
  - 初期値とエポックごとのシャッフルは ChaCha20(`--seed 2020`)から取った。プロジェクトの乱数規則に従ったので、スパイクと同じ乱数列ではない。
- **形とパディング**: d_in 4、隠れ層 10 → 16、出力 3 → 4 にゼロでパディングした。レイアウトは `Layout { slots 2^14, d 16, batch B }`。
  - batch 1 は B = 1。
  - batch 20 は B = 32 で、12 レーンは trainer の有効レーンマスクで勾配から除く。このマスクは微分係数の平文に畳み込まれるので、レベルは消費しない。
  - 150 = 120 学習 + 30 テストで、120 / 20 = 6 バッチがちょうど割り切れる。部分バッチは出ない。
  - 各層の対角数は m = min(n_out, n_in) = 4(W1 16×4、W2 4×16)。
- **パラメータ**: `seal_2020`(N = 2^15、{60, 40×9, 60}、Δ = 2^40、レベル 9)。両方の走行でこれを使い、`seal_2020_l10` は不要だった。

### 発見: 複製ブロックのコピーが指数的に乖離する(修正済み)

最初の 400 epoch 走行(Task 30 のままの `ClientRefresher`)は、**epoch 30 で発散した**。CKKS のオーバーフローで、重みは 1e31 になった。

- 双子との重み誤差は指数的に増えた: 2^-20(epoch 0)→ 2^-13.4(13)→ 2^-5.8(20)→ 2^-2(24)。そのあいだ、双子は正常に学習していた(loss 0.03)。
- **平文の学習自体はカオス的ではない**。同じネットワーク・分割・lr で、平文学習の各ステップの全重みに N(0, (2^-22)²) を加えても、400 epoch で差は 2^-15 程度にとどまった(6 シードで同じ傾向、numpy で確認)。
- **原因**: batch 20 のレイアウト(d 16 × B 32 = 512 スロット)は 2^14 スロットに 32 回複製される。
  - 各コピーは自分のノイズを持ち、学習ステップは各コピーを別々に計算する。
  - ブロック境界をまたぐ回転は、隣のコピーを混ぜる。
  - 診断ログでは、レーン方向の乖離は 2^-19.4 → 2^-17.4 のランダムウォークだった。一方、ブロック方向の乖離は 2^-19.2 → 2^-12.0(13 epoch)と指数的に増え、重み誤差がそれを追った。
  - レーンのコピーは、更新が全レーンに同じ値で配られるので戻る力も増幅も無い。ブロックのコピーは、それぞれが自分の勾配で更新され、境界で混ざる。
- **修正**: `ClientRefresher::with_layout(layout)`。refresh の際に全ブロックをブロック平均で置き換えてから再符号化する。
  - 全パック済みベクトルはブロック周期的なので、この操作は正確である。コピーのノイズの平均化にもなる。
  - 修正後は、ブロック方向の乖離は全期間 2^-25 前後で一定、レーン方向は 2^-21.9 → 2^-17.3(400 epoch)。
  - Task 31 のレビュー後(6f9fa6f)、これを既定にした。`Refresher::bind_layout` を必須のメソッド(既定実装なし)にし、`Trainer::new` が必ず呼ぶ。`with_layout` は同じことをするビルダーとして残る。乖離の回帰テストも加えた。上の 400 epoch 走行(`iris_20.json`)は、この変更の前の `with_layout` を明示した版で走らせたもので、ブロック平均の処理は同じ。
- **影響範囲**:
  - Task 32 の MNIST(n16_train、d 1024 × B 32 = 32768 = スロット数)は単一ブロックなので影響しない。
  - M3 のブートストラップ refresh にはクライアントの再配置が無い。複製レイアウトを使う場合は、サーバ側でのブロック平均(log2(複製数) 回の回転 + 加算、定数 1/複製数)、または単一ブロックのレイアウトが必要になる。
  - レーン方向のランダムウォークは、さらに長い走行ではレーン平均でも抑えられる(重み・バイアス・速度は全レーンで同じ値なので)。今回は不要だった。

  - この比はバイアス勾配の +20 KS / 更新を **hekit 側だけ**に数えている(ReBoot 側のモデルにバイアスは無い)。除くと 613 / 32 = 19.16 で 0.518。
- **M0 の見積もりからの推移**: M0 の対話モードの比は **0.222**(B = 48、`spikes/RESULTS.md` Task 6)だった。同じ指標を補正後の式で B = 48 にすると **約 0.39**、B = 32 の実測は **0.535**。つまり M0 の対話モードの見積もりは楽観的すぎた(B = 48 で約 1.75 倍)。差のほとんどは**サーバ側の複製**(240 KS / 更新 = 7.5 / サンプル)。
  - reduce-only の変種(`docs/layout.md` §3、レーン 0 を読み直す refresh)なら 393 / 更新 = 12.3 / サンプル、比 0.33。複製を残すかどうかは M3 の bootstrap refresh の形で決まる。
- **RQ1 の「30% 以上少ない」(比 < 0.70)は、この指標では成り立つ**: 0.535(B = 32 実測)、0.39〜0.42(B = 48 の式)。
- **B = 48 の式(2 暗号文、走らせていない)**: モデル 395 / 更新に同じ補正(baby と分割は暗号文ごと)を足すと、395 + 240 + 28 + 20 − 4 + 12 = **691 → 14.4 KS / サンプル**(比 0.39)。Dedicated なら 679 → 14.1。
  - この 691 は、勾配の relin を 2 暗号文にまたがって遅延させ、更新ごとに m 回で済ませる前提。モデル(§5 の 4)はこの前提を置いている。
  - hekit には今、複数暗号文のバッチも、暗号文をまたぐ遅延 relin も無い。その場合は relin が +48 で **739 → 15.4 KS / サンプル**(比 0.42)。
- RQ1 の全体の表と判定は §1・§2 に書いた。

## 5. 逸脱の一覧

計画・ブリーフ・論文からの逸脱と、結果の読み方に効く判断。出所は SDD の作業記録(Ruling / minor / Note)と各節。

**学習層(Task 25〜30)**
1. **バイアスは NAG の下でも素の SGD**。Task 28 の NAG API にバイアスの運動量が無い(Task 30、Task 32 で同じ)。eMLP-1 の ReBoot レイアウトの行にはバイアス自体が無い(下の 19)。
2. **線形の出力層のため `activation::Identity` と `Activation::constant_derivative` を追加した**(Task 32 のスコープ拡張)。trainer に線形の出力層が無かった。
3. **seal_2020 は 9 レベルを余裕 0 で使い切る**。lr / n をマスクの乗算に畳み込んだときだけ 9 に収まる(Task 25、30、31)。`seal_2020_l10` は使わなかった。
4. **lr / batch をマスクの乗算に畳み込んだ**ので、`Sgd::step` は lr / batch を掛け済みの勾配を受け取る。ブリーフの `W − lr·dW` という API とは形が違う(Task 28 の Ruling)。
5. **マスク**: 親の level ruling (1)(0/1 マスクをスケール 1 の整数平文にする)は、スロット領域の 0/1 マスクが一般に整数多項式にならないので使わなかった。マスクを使わない設計を優先し、必要ならスケール q_l で符号化して rescale する(1 レベル、厳密スケール)(Task 25 の Ruling、親が訂正済み)。
6. **Layout は d·batch | slots(等号ではなく割り切れる)を要求する**(Task 25 の Ruling)。
7. **BSGS の relin は giant の本数**(計画の文面は 1)(Task 26 の Ruling)。
8. **重みのサーバ側複製を残した**(非対話版の M3 に忠実にするため)。そのため対話版でも m log B の複製の回転がかかり、M0 の対話版モデルとの差の大半になった(§4)。Task 32 の 10% 確認は、対話版モデルにこの複製項を足したものと比べた(Task 25 の Ruling)。
9. **weight decay は延期**。ReBoot の値は `spikes/reboot/RUN.md` にしか無く、hekit では適用していない(`docs/layout.md` の該当箇所)。

**Iris(Task 31)**
10. **複製ブロックのコピーの乖離と `bind_layout` の修正**(§3)。最初の走行が epoch 30 で発散した。ブロック平均の refresh で直し、レビューで `Refresher::bind_layout` を必須にして既定にした(6f9fa6f、回帰テスト付き)。M3 のブートストラップ refresher は、サーバ側でブロック平均するか、複製レイアウトを拒む(R-M3-3)。
11. 損失の定数 2/3 を学習率に畳み込んだ。隠れ層 10 → 16、出力 3 → 4、batch 20 → 32 レーンにゼロでパディングした。乱数は ChaCha20 で、分割は M0 スパイクのものを使った(§3「論文のパラメータからの逸脱」)。`iris_1_timing.json` の `"epochs": 400` は timing モードでは使われない古いフィールド(§3)。

**MNIST(Task 32)**
12. **B = 32 で走らせた(ReBoot は 48)**。d·B = 2^15 でちょうど 1 暗号文になる。B = 48 は 2 暗号文になるので、式による見積もりだけ(§4)。M3 では B ∈ {32, 64}(64 は 32 レーンのマイクロバッチ 2 つ、R-M3-4)。
13. **転置鍵は Reuse**(31 本、≈ 9.7 GB)。Dedicated(45 本、≈ 13.9 GB)はメモリが厳しいため。Reuse は Dedicated より +12 KS / 更新(§4)。
14. シャッフルなし(学習データの先頭 1024 件をファイル順に)。初期値は PyTorch の `nn.Linear` の既定。eMLP-1 の設定は JSON を読まずにバイナリに転記した(依存を増やさないため)。
15. **`results/mnist_emlp1.json` は手で加えたフィールドを含む**(出所は JSON の `provenance`)。ビルドの記録は Task 34 で訂正した(693040a ではなく ce2ab74 前後 + 未コミットの変更。値には影響しない)。

**ReBoot レイアウト(Task 33)**
16. **(r, c) = (1024, 32)**。ブリーフの (16, 2048) は 784 入力を持てない。論文 §4.1 の規則とコストモデルの `reboot_rc` は (1024, 32) になる(Task 33 の Ruling)。
17. **見出しは Lazy(バッチの勾配和で relin 1 回)、PerSample(積ごとに relin、コストモデルの既定)は「仕様どおり」として併記**。relin の方針は論文に書かれていないので、ReBoot に寛大な側を見出しにした。PerSample は 256 件(8 バッチ)だけ走らせ、1 epoch の時間は外挿。
18. **ReBoot の Alg. 1 の 10 行目(遅延した勾配)はモデル化していない**。精度にだけ効き、鍵切替の数には効かない。Alg. 1 は 1 サンプルずつの学習で、ミニバッチの和はブリーフとコストモデルの読み方に従った。
19. **ReBoot レイアウトにはバイアスが無い**(鍵切替には影響しない)。平文の双子もバイアス無し。なので精度は diag hekit の行とは比べられない。更新はクライアントが平文の NAG で行う。
20. **`results/mnist_reboot_layout.json` はバイナリの生の出力ではない**。2 つのモードの出力とログをスクリプトでまとめたもの。最初はコミットしていない使い捨てのスクリプトだったが、Task 33 の修正ラウンド(66e363b)で `tools/reboot_layout/assemble.py` としてコミットされ、`provenance` ブロックが加わった。測定値は変わっていない。

**RQ1 の指標**
21. **主指標は回転 + relin**(鍵切替は relin で起きる)。計画 §4.3.2 の字義どおりの「回転 + ct-ct 乗算」は §2.1 に併記した。対話版なのでブートストラップは数えていない(spec の指標は M3)。
22. **計画の「1 サンプル・1 層あたり」(§4.2)と「1 サンプル・1 epoch あたり」(§4.3.2)の揺れ**: ネット全体の 1 サンプルあたり(1 epoch 平均)で数えた(M0 と同じ)。
